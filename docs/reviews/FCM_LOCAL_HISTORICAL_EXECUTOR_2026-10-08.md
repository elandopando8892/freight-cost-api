## Benchmark y definición

Se reutilizó [la comparación anterior](FCM_HISTORICAL_TRANSITION_REVIEW_2026-10-08.md) y se inspeccionaron módulos, helpers de backup, migraciones y --help del Prisma5.22 instalado. No infraestructura, librería, suscripción o cargo adicional. La capacidad es estándar; no se presenta como innovación.

La [documentación Prisma](https://www.prisma.io/docs/orm/v6/prisma-migrate/workflows/patching-and-hotfixing) distingue SQL aplicado e historial reconciliado. Se usa como referencia de flujo, comprobando los comandos reales5.22, sin transferir flags7. [PostgreSQL pg_dump/pg_restore](https://www.postgresql.org/docs/16/backup-dump.html) brinda el mecanismo reutilizado para recuperar una base completa. Se revisó el changelog Supabase de nuevo; no se cambia SDK, servicio o esquema compartido.

Objetivo de cierre local: preservar SQL de origen, aplicar sólo pendientes con historial nativo, probar respaldo restaurado antes de aplicar, conservar registros históricos/roles/tenant/importes, admitir sólo el drift legado exacto, y detener fallo/replay sin duplicar. El flujo es preparar → cotejar inventario → respaldar/restaurar → migrar → comprobar datos/ledger/diff → VERIFIED. No toma decisiones de publicación ni autenticación.

## Implementación y límites

- buildHistoricalMigrationPackage devuelve46SQL originales, schema y provider lock, fingerprints y13pendientes para la fixture inicial33. La fuente original47 no se edita; la exclusión única queda explícita. Preparar no autoriza ejecutar.
- verifyHistoricalCoexistence exige que todas las pendientes excepto el retiro hayan terminado, checksums válidos y preservación multiset del ledger inicial (incluidos rolled_back). Sólo admite DROP INDEX User_kindeId_key y DROP COLUMN User.kindeId en la diferencia hacia el modelo; cualquier otra diferencia, retiro aplicado, registro cambiado o migración incompleta bloquea. No relaja gates de release existentes.
- El ejecutor exige Windows/Docker local por named pipe, nombre/label/ID propios, puerto127.0.0.1 y DB de fixture fcm_hist_*. No lee DATABASE_URL ni credenciales de la sesión, no acepta URL remota y usa un entorno CLI reducido. No API/endpoint público, ni cambio de trust/OAuth.
- Coteja la proyección completa de usuarios y ledger antes de escribir. Materializa SQL de origen en un directorio fresco de D:/andre/validation y verifica bytes antes de cada CLI. Referencias, labels y hashes son controles cooperativos, no pruebas infalsificables de autoridad.
- pg_dump integral se restaura en una DB nueva del mismo contenedor. Coteja hashes de todas las tablas públicas y una diferencia de esquema vacía antes de aplicar. La copia incluye el manifest privado y comprueba su binding. No se limita a contar usuarios.
- Tras aplicar, compara todas las columnas preexistentes de todas las tablas públicas (excluyendo las filas nuevas del ledger); coteja además el hash de cada fila completa original del ledger. Se preservan importes y campos originales. La verificación del schema mediante Prisma no constituye auditoría exhaustiva de ACL/triggers ni aceptación operativa.
- Manifest privado por DB: STARTED antes de backup, UNCERTAIN antes de lanzar migrate, VERIFIED sólo tras las comprobaciones. Un segundo intento se rechaza incluso con un inventario nuevo. Ante fallo, no catch/retry, reset, resolve o rollback automático. Las migraciones no son un único commit global: puede haber pasos previos aplicados; se conservan como tales y el fallo nativo queda visible.
- El rollback requiere restauración separada del respaldo verificado bajo autoridad correspondiente; el ensayo conserva las DB restore con33registros. No borra/reemplaza una fuente fallida ni adopta bases de otros trabajos.

## Pendiente y rollback

Después requiere promoción del par del mismo commit, política exacta sales/JG, membresía gobernada y OAuth/permisos reales. El ejecutor local no abre esa ruta ni convierte una snapshotOct7 en evidencia actual.

Rollback del código: revertir sólo el checkpoint de este bloque, preservando cambios ajenos. Sin rollback remoto necesario.
